## Frontend App Rules (`apps/web`)

- Read `../../AGENTS.md` and `../../docs/architecture.md` first.
- Pages and components (`src/app/`, `src/components/`) may import only `@yushiguang/sprint-contracts` (types),
  `@yushiguang/sprint-domain` (pure rules), `@/backend-api`, `@/components` and `@/ui`. The boundary check
  enforces this, and also checks the aliases in `tsconfig.json` and `next.config.mjs`.
- The look comes from `src/ui/kit.css`, a copy of the Unified UI canvas styles: keep it identical
  to the canvas and put app-only rules in `src/ui/app.css`. Pages build from the parts in `@/ui`.
  Anything that can't match the canvas goes in `docs/ui-gaps.md`.
- `src/backend-api/in-process.ts` is the composition root (`client.ts` is the `BffClient`
  interface): the only file that builds the apps and imports `@yushiguang/sprint-platform-impl`. It is the
  default module behind `@yushiguang/sprint-client-impl`; `index.ts` takes the client through that alias and
  never imports `in-process.ts` itself (the boundary check enforces it).
- UI text uses plain words (for example "the optimiser", never the method name).
- Before pushing, from the repo root: `npm run check && npm run build`; for flow changes also
  `node apps/web/scripts/e2e-check.cjs`.

WORKFLOW — start every page from a template, never from scratch:
1. `astryx build "<idea>"` — names the template to scaffold from and the parts it lacks.
2. `astryx template <name> <path>` — scaffold it; keep its frame, gap and padding; replace the content.
3. `astryx template <Block>` for parts it lacks; `astryx component <Name>` to read props before using one.
Changing an existing page? Keep it: skip step 2 and add blocks/components inside its sections.
Before you deliver a build, run `astryx doctor --built <dir>`; don't deliver it if it fails.

RULES:
- No <div> — components handle all layout and spacing.
- Read `astryx docs layout` before changing a template's frame.
- Dense data = rows (Table, List/Item), not Card-wrapped lists. Badge = counts only.
- Style with component props first, then tokens (var(--color-*|--spacing-*|--radius-*)). No raw hex/px. No StyleX/Tailwind compiler here — don't use xstyle/utility classes directly. Some templates use StyleX and need a compiler plugin; see `astryx docs styling-overview`.
- THEMES: palettes and custom colors go through the theme, never :root overrides. To make or change a theme (colors, fonts, corners, spacing, a look from a picture), prefer the experimental theme editor over hand-written theme files: `astryx experimental theme editor new <name> --like neutral`, then `editor set <name> <thing> <value>` or `editor how "<what you want>"`; wire it with `astryx theme add <name>`; after each change look at it with `astryx experimental theme editor show <name> --png` and open the PNGs it writes (changes nothing in the app); a theme change is not done until you have looked at the pictures. In code, extend an imported theme to customize it; `theme eject <slug>` only forks source. See `astryx docs theme`.
- SELF-CHECK: re-read the file; replace any raw <div>/<span>, imported .css/@apply, or hardcoded #hex/px with the component or a token.
