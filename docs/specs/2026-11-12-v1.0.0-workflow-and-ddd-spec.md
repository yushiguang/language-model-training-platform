**Target Release:** `1.0.0` (Semantic Versioning 2.0.0; supersedes `0.1.0` MVP)  
**Date:** 2026-11-12  
**Target:** External Agent (architecture, contracts, domain, services, and web app)

## 1. Context, Versioning, and Legacy Cleanup

### 1.1 Semantic Versioning (`0.x.x` -> `1.0.0`)
- The browser-only MVP line uses `0.x.x` (`0.1.0`).
- This specification defines **`1.0.0`**, the first production-targeted release. Upon completing this specification, bump `version` to `"1.0.0"` in the root `package.json` and every workspace `package.json` (and default `NEXT_PUBLIC_APP_VERSION` to `'1.0.0'`).
- Note on `@tsp/*`: `tsp` stands for *"Training Set Platform"* (the repository's original working name before it was named **Sprint**). Keep `@tsp/*` package scopes and `tsp_*` metric prefixes stable during `1.0.0` to avoid unnecessary adapter churn unless a dedicated rename PR is scheduled.

### 1.2 Usability Findings Addressed
1. **Cognitive inversion at project start**: Asking non-ML users to define an abstract JSON output schema (`Setup -> Evaluation -> Models`) before capturing their prompt idea or inspecting data caused confusion. Maintaining label definitions in both `Schema` and free-text `PromptVersion.template` also caused drift and risked invalidating gold labels when wording changed.
2. **Conflating two distinct workflows**: Coupling a ~500–3,000 example prompt-tuning dataset with a 100,000+ example production dataset via a manual `Eval / Test / Train` split slider led to user errors (such as setting `Eval = 0`), wasted resources early in a project, and cluttered the UI with an unnecessary `Test set` concept.
3. **Label imbalance hurting optimisation**: Under Macro-F1, a rare label value with only 1–2 eval examples disproportionately drags down headline scores and starves the Optimiser of learning examples, causing repeated negative rounds. Users lacked dataset distribution diagnostics, incremental sampling/upload, and example pruning.
4. **Upcoming microservice migration**: Each backend module will be deployed as an independent microservice communicating over strict RPC IDLs (such as Apache Thrift), potentially implemented in different languages, with the agent runtime replaceable by a server-side orchestration service. Domain/business logic must be cleanly separated from transport and infrastructure adapters.

### 1.3 Legacy Dead Code to Remove During `1.0.0` Implementation
Cleanly delete obsolete `0.x` artifacts rather than carrying compatibility shims into `1.0.0`:
- **Removed routes & flows**: `apps/web/src/app/(project)/setup/`, `apps/web/src/app/(project)/training-set/` (deferred to the standalone Batch Labeling project workflow), `apps/bff/src/services/setup.ts` (replaced by project settings), `apps/bff/src/services/training.ts` (`labelTestSet`, `testRuns`, `finalRunPlan`), and Dataset `<CheckLabels>` / `checkLabels` / `check_schema`.
- **Obsolete reopen & budget shims**: `reopenGold` / `GOLD_REOPEN` in `apps/bff/src/services/mismatches.ts` (superseded by in-place review saving), `budgetUsd` / `extendBudget` / `overBudget` in `apps/labeling` (decided 2026-11-06: tasks run without budget caps), and unused `Recommendation` collection/types.
- **Obsolete telemetry entries**: Prune dead `0.x` event/label entries (`gold_skipped`, `gold_mismatch_reopened`, `test_answers_requested`, `compare`, `report` routes, `schema_agent` once merged) from `packages/contracts/src/telemetry.ts`.
- **Unused UI exports**: Remove unused `UiProvider` or dead helpers in `apps/web/src/ui/index.tsx` if unreferenced.

## 2. Dual-Workflow Product Architecture

Sprint separates **reusable domain capabilities** (structured prompts, dataset management, human/model labeling, scoring, and optimisation) from **workflow orchestration**:

### 2.1 Workflow A: Prompt Tuning Project *(Implemented in `1.0.0`)*
A focused **4-step linear workflow** shown in the top stepper:

1. **Prompt Design** (`/prompt-design`) — Capture the user's classification idea immediately: select input features, define label fields and per-value definitions, and state general/fallback rules to create `v1`.
2. **Eval Dataset** (`/dataset`) — Upload or sample the evaluation dataset (hundreds to ~3,000 examples), inspect distribution diagnostics, append targeted examples, or prune noisy/excess items. Every valid example in this project belongs to the eval dataset (internally stratified 50/50 into `optimiserHalf` and `heldOutHalf`).
3. **Gold Labels** (`/gold`) — Label eval examples (`To label | Labeled`) and adjudicate model disagreements (`Mismatches`: `To review | Reviewed`) with multi-comment support.
4. **Prompt Tuning** (`/prompt`) — Score versions, inspect metrics, run `Improve with AI` or `Auto Optimise`, compare structured diffs, copy/export the compiled prompt, and mark the tuning project finished.

### 2.2 Workflow B: Batch Labeling Project *(Contracts designed in `1.0.0`; UI deferred)*
Large-scale dataset production (e.g., 100k+ items) is modeled as a separate `ProjectKind = 'batch_labeling'` project that links to a Prompt Tuning project:
- Carries `sourceProjectId` and `sourcePromptVersionId` (inheriting its `LabelSignature`, compiled `StructuredPrompt`, and `ModelSettings`).
- Reuses the shared `Dataset` and `Labeling` service contracts without duplicating prompt-tuning state.
- **Scope for `1.0.0`:** Define `ProjectKind` and the linking fields in `@tsp/contracts` and `@tsp/catalog` so contracts are forward-compatible; **do not** build the Batch Labeling UI pages yet.

### 2.3 Project-Level Settings (Model & Evaluation Thresholds)
`Labeling model` and `Evaluation settings` are no longer workflow steps:
- **Defaults at creation**: Creating a Prompt Tuning project initializes `ProjectSettings` with the first active labeling endpoint (`maxOutputTokens: 1024`, `temperature: 0` when supported) and `DEFAULT_THRESHOLDS` (`mode: 'default'`, `macroF1: 0.80`, `minEval: 20`), with `settingsConfirmed: false`.
- **Persistent entry**: Add a `Settings` button in the right section of the top island (`Shell.tsx`) that opens the **Project Settings dialog** (`Evaluation` and `Labeling model`).
- **Pre-execution confirmation**: Before the first paid scoring or optimisation run starts (e.g., clicking `Next: Prompt Tuning` from Gold Labels once eval gold is complete, or manually clicking `Score` / `Auto Optimise` while `settingsConfirmed === false`), open the Project Settings confirmation dialog once. Saving sets `settingsConfirmed: true`.
- **Evaluation `Default` panel (Feedback #5)**:
  - Both `Default` and `Custom` display the right-hand `Checks` table side by side with the `Pass rule` radio options.
  - When `Default` is selected, render the exact thresholds (`Macro-F1` On at `0.80`, `Value F1` Off `–`, `Precision` Off `–`, `Recall` Off `–`, plus `Invalid outputs` locked On at `<= 1%`) with all switches `locked` and inputs `disabled`.
  - Remove dashed-underline hover tooltips (`<Hov>`) from `Default`, `Custom`, and check names here; instead render each check's plain-language explanation directly as a muted subtitle line under the check name.

### 2.4 Projects List Simplification & Confirmed Deletion (`apps/web/src/app/page.tsx`)
1. **Remove `Current step` column**:
   - Simplify the Projects table columns to `Project` (link), `Created` (`dateTime`), and a right-aligned action column `Delete` (ghost destructive button).
   - Remove the per-project `loadProjectState(p.id)` loop on the home page so `/` loads with a single lightweight `listProjects()` call.
2. **High-risk `Delete project` with exact-name confirmation**:
   - Clicking `Delete` opens a confirmation `Dialog` warning that deleting the project permanently removes its dataset, gold labels, comments, prompt versions, reports, optimisation history, and chat messages.
   - Include a text input asking the user to type the exact project name (`confirmText === project.name`); keep the destructive `Delete project` button disabled until it matches.
   - Implement `deleteProject({ projectId })` on `BffContract` / `CatalogContract` / `LabelingContract`: abort any active sampling, labeling, or optimisation run for the project first, cascade-delete all associated records across collections, emit `project_deleted` telemetry, and refresh the list.

### 2.5 Auto-Start Manager (`dueStarts` & `tick`) Guardrails in the 4-Step Flow
Keep the declarative `dueStarts(state)` + keyed idempotent `tick({ projectId })` architecture (`packages/domain/src/auto-start.ts` and `apps/bff/src/services/work.ts`), updated for the new workflow order:
- Because Step 1 (`Prompt Design`) now creates `v1` **before** an eval dataset exists, `dueStarts` MUST require:
  1. Valid eval dataset ready (`examples.length >= config.dataset.minEvalHard`);
  2. At least `config.dataset.minEvalHard` eval examples are gold-labeled, with at least 2 in each half (scoring never waits for every example; see 4.4), OR explicit user click on `Score`;
  3. Project settings confirmed (`settingsConfirmed === true`).
- Once those conditions hold, creating/saving a new non-optimiser `PromptVersion` (or reopening a page with a `paused` eval scoring task) automatically starts/resumes scoring as before, while `Auto Optimise` remains strictly user-initiated.

## 3. Structured Prompt Model (Merging Schema and Prompt)

### 3.1 Separating Label Signature from Prompt Versions
Split what used to be `Schema` + `PromptVersion` into two layers so definition refinements never invalidate human gold labels:

1. **`LabelSignature` (bumps `schemaVersion` only when changed)**:
   - Fields: `name: string`, `kind: 'single' | 'multi'`, `min?: number`, `max?: number`, and `values: string[]` (ordered value names only).
   - Adding, removing, or renaming a field or value name, or changing `single`/`multi` bounds, increments `schemaVersion` (archiving old reports and flagging stale gold labels).
2. **`StructuredPrompt` (stored on each immutable `PromptVersion`: `v1`, `v1.1`, `v2`, ...)**:
   - `taskSummary: string` — 1–2 sentences describing what items are being classified and why.
   - `features: FeatureSelection` — Ticked feature keys (`video`, `photo_text`, `metadata`).
   - `fields: StructuredFieldPrompt[]` — Mirrors `LabelSignature`, holding per-value `definition: string` and optional field-level tie-break notes.
   - `generalRules: string` — Cross-field decision rules, fallback behavior when evidence is ambiguous/missing, or handling noisy features.
   - `images: PromptImage[]` — Optional reference images.
   - **Editing `taskSummary`, `features`, any value's `definition`, or `generalRules` creates a new `PromptVersion` (`major.minor`) WITHOUT bumping `schemaVersion` or invalidating gold labels.**

### 3.2 Deterministic Prompt Compilation & Read-Only Full Preview
Pure function `compilePrompt(structured: StructuredPrompt, signature: LabelSignature): string` in `@tsp/domain`:
1. Task summary block.
2. Input features block: automatically generated from `structured.features` in canonical order (`Label: {{Key}}`), noting empty features render as `none` (eliminating `not_ticked`, `unused_feature`, and `broken_braces` errors by construction).
3. Per-field rubric block: field name, cardinality rule (`Choose exactly 1` vs `Choose min to max`), and each `value: definition`.
4. General rules block (`structured.generalRules` when non-empty).
5. Output format block: strict JSON output instructions with exact field keys and allowed value names (followed at runtime by `REASON_LINE` in `@tsp/labeling`).

**UI Presentation (`Prompt Design` & `Prompt Edit`)**:
- **Default view**: Modular structured editor with plain-language helper guidance:
  1. **Output Labels & Definitions** — Field list on the left + Field editor on the right, explaining how fields/values drive human labeling, output validation, and scoring, and how definitions guide the model.
  2. **Input Features** — Feature groups (`Video`, `Photo and text`, `Metadata`) with hover descriptions.
  3. **Task & General Rules** — `Task summary` and `General / fallback rules`.
- **View Full Prompt**: A `View full prompt` dialog/drawer in the page header displays the live compiled prompt string read-only with a `Copy prompt` button.
- **Importing existing prompts**: Pasting an existing raw prompt into `Ask AI` lets `Prompt helper` parse it into a structured `StructuredPrompt` proposal. The import is lossy by nature (few-shot examples, output-format instructions and ordering have no slot), so the proposal MUST carry an `unmapped: string[]` list of the passages it could not place, shown in the AI Suggestion card as *"Not carried over"*. The helper never drops text silently, and the user's pasted prompt stays in the chat history.
- **Structured Word Diffs**: In `Prompt Edit`, word-level diff marks (`diffWords` + `withReasons`) highlight changes directly inside modified `definition` and `generalRules` blocks, and badge added/removed `features`.

### 3.3 Layout & Truncation Fixes in Structured Prompt Editor (Feedback #3 & #7)
- **Full-visibility multi-line inputs (#3)**: Replace single-line `<input>` on value `Definition` (and `General Rules`) with an auto-growing multi-line `<textarea>` (`rows={1}`, `white-space: pre-wrap`, `overflow-wrap: anywhere`), and allow rows in the value list to grow vertically (`height: auto; vertical-align: top; padding: 8px 12px`) so long definitions are never clipped.
- **No panel overflow (#7)**: In `FieldEditor`, set `flex-wrap: wrap` and `min-width: 0` on the field header control row, constrain card width (`min-width: 0; max-width: 100%; overflow: hidden`), and narrow the left `Fields` navigation column from `360px` to `280px` so `Field name` + `Single/Multi-select` + `Choose [min] to [max]` + `Remove field` stay strictly inside the white card even when the 400px `Ask AI` drawer is open.

## 4. Eval Dataset Governance and Balance Diagnostics (Feedback #6 & #10)

### 4.1 Removing Unexpected Dataset Agent Card (Feedback #6)
- Delete `<CheckLabels>` from `apps/web/src/app/(project)/dataset/page.tsx` and remove `checkLabels` / `check_schema`.

### 4.2 Eval Dataset Rules & Stratified Halves (Feedback #10)
- **Minimum size**: Require `validExamples >= 4` to approve the `Eval Dataset` gate (at least 2 examples in `optimiserHalf` and 2 in `heldOutHalf`; `0` is impossible). When `4 <= validExamples < thresholds.minEval` (default 20), allow advancing with an inline advisory banner: *"Fewer than 20 examples: scores will be rough until you add more examples."*
- **No pass verdict on a rough reading** *(review amendment, approved 2026-11-12)*: while the scored (gold-labeled) eval examples number fewer than `thresholds.minEval`, the score is shown with a `Rough reading` tag instead of `Passed` / `Below threshold`, the threshold line stays on the chart, and the `Finish` / export gate stays closed. `Auto Optimise` may still run, and its end line says the result is a rough reading.
- **Stratified 50/50 split (`assignEvalHalves` in `@tsp/domain`)**:
  - Initially assign `optimiserHalf` deterministically by hash (`50% / 50%`).
  - **Strict holdout invariant**: Once any helper/optimiser has read examples on a project (`holdoutLocked`), an example already assigned `optimiserHalf === false` MUST NEVER flip to `true`. Newly appended examples or pre-lock gold-labeled datasets use stratified assignment so rare values are balanced across both halves.

### 4.3 Dataset Management & Label Balance Diagnostics
On the `Eval Dataset` page (once examples exist):
1. **Incremental Append Actions**:
   - Allow adding data at any time without wiping existing examples or gold labels: `Append upload` (deduplicated by `externalId`) and `Append sample` (sample `N` additional unseen items).
2. **Label Balance & Coverage Card** (shown once gold labels exist):
   - Renders `LabelDistribution` across gold-labeled eval examples (plus unlabeled count).
   - **Rare-value warning**: Flag any value with `< 4` gold examples (or `< 2` in either half) in amber/red, warning that a single miss heavily lowers Macro-F1 and prompting targeted upload/sampling.
   - **Dominant-value hint**: Flag values exceeding `70%` of labeled examples (when `total >= 30`), offering optional downsampling.
3. **Pruning / Removing Examples**:
   - **Single-example removal on Gold Labels**: Add a `Remove example` ghost action on `ExampleCard` to drop broken or out-of-scope items from the eval dataset.
   - **Batch / targeted pruning on Eval Dataset**: Support removing unlabeled excess items or randomly downsampling examples of an over-represented gold label down to a target count `K` (`pruneDatasetExamples`).

### 4.4 Scoring While the Dataset Changes *(review amendment, approved 2026-11-12)*
- **Appending never freezes scoring.** A version is scored on the eval examples that have a gold label at the time of the run. Appended examples without a gold label are `pending`: they are excluded from scores and shown as a count (*"12 new examples wait for gold labels"*) on `Eval Dataset` and next to the score.
- **Stale, not blocked.** When gold labels are added, changed or removed after a version was scored, that version's score is marked stale and the existing manual `Rebuild scores` action brings it up to date. Nothing rebuilds automatically.
- **Removals leave a trail.** Every removal (single `Remove example` or `pruneDatasetExamples`) writes a `DatasetRemoval` record: `exampleId`, `externalId`, `half`, the gold label at removal, `reason` (`broken` | `out_of_scope` | `downsample` | `excess_unlabeled`), `removedBy`, `removedAt`. Removed examples are soft-deleted and restorable from a `Removed (N)` list on `Eval Dataset`. The count of removed gold-labeled examples is shown next to every score computed after the removal, so a score raised by deleting hard examples is visible as such.
- **Removal keeps the holdout invariant.** Removing or restoring an example never changes any other example's half.

### 4.5 What the Held-Out Half Does and Does Not Prove *(review amendment, approved 2026-11-12)*
- The held-out half is used to pick the best version and to stop the Optimiser, so after several rounds it is no longer an untouched test. `1.0.0` keeps the `0.x` **confirm a pass** step (a passing version is confirmed on a fresh relabel of the held-out half) as the guard, and the UI never calls the held-out score a test score.
- A real untouched test set belongs to Workflow B (Batch Labeling Project, 2.2): its contracts reserve a `testSet` that no helper, optimiser or Prompt Tuning score ever reads.

## 7. DDD Architecture & RPC/IDL-Ready Service Boundaries

Split the codebase strictly into **Layer 1: Domain & Business Services** and **Layer 2: Infrastructure & Transport Adapters** so every service contract maps 1:1 to strict RPC IDLs (such as Apache Thrift).

### 7.1 Strict IDL-Compatible Contracts (`packages/contracts`)
1. **Pure JSON / IDL structs only**:
   - Replace all `Map<K, V>` and `Set<T>` with `Record<string, V>` or typed arrays.
   - Replace union feature values `Record<string, string | string[]>` with explicit `FeatureValue { text?: string; items?: string[] }` (or separate `textFeatures` / `listFeatures` maps).
   - Replace `unknown` proposal payloads with typed `StructuredPromptProposal`.
2. **Request / Response struct convention & ID-only mutations**:
   - Never pass client-held `ProjectState`, `PromptVersion`, or `AgentProposal` objects back into BFF methods; pass IDs and explicit input structs (`tick({ projectId })`, `scoreVersion({ projectId, promptVersionId })`, `closeProposal({ projectId, proposalId, decision })`).
   - Support optional `idempotencyKey?: string` on paid/mutating start requests (`scoreVersion`, `startOptimiser`, `createVersion`).
3. **No function callbacks across service calls**:
   - Inject `LlmGatewayContract`, `AgentToolHost`, and `EventStreamPort` at construction time (`createAgentRuntime(deps)`), keeping `runTurn(req): Promise<RunTurnResponse>` pure data.
4. **Enterprise Extension Ports (`packages/contracts/src/platform-api.ts`)**:
   - Define `RequestContext { tenantId?: string; userId?: string; requestId?: string }` and optional platform ports (`TenantConfigPort`, `AuthorizationPort`, `JobQueuePort`) with permissive single-tenant stand-ins in `@tsp/platform`.

### 7.2 Extracting `@tsp/optimiser` (`apps/optimiser`)
Move the stateful GEPA optimisation loop out of `apps/bff` into `apps/optimiser` (`@tsp/optimiser`):
- Implements `OptimiserContract` (`startRun`, `stopRun`, `retryRun`, `getRun`, `listRuns`).
- Imports `@tsp/contracts` and `@tsp/domain` only; receives `CatalogContract`, `LabelingContract`, `AgentRuntimeContract`, `LockPort`, and `TelemetryPort` via dependency injection.

### 7.3 Separating Frontend `BffClient` Transport from Composition Root
Split `apps/web/src/backend-api/` into:
- `client.ts` (typed `BffClient` interface used by all UI components).
- `in-process.ts` (default browser composition root wiring `@tsp/platform-impl` and all services for standalone/dev builds; replaceable by a pure `fetch`/SSE HTTP adapter in microservice deployments without bundling backend apps into the browser).
- **Standalone browser acceptance guarantee**: Keep `@tsp/platform` stand-ins (`localStorage` DB, `simulatedModels`, `scriptedAgent`, sample examples/media) and `in-process.ts` 100% functional for every `1.0.0` feature so the full product can be interactively accepted in a local browser (`npm run dev` / `npm run build`) **before** any microservice migration begins.

### 7.4 Centralised `SystemConfig` (Eliminating Hardcoded Magic Numbers)
Consolidate all ~30 scattered thresholds, limits, and heuristic coefficients into a single typed `SystemConfig` (`packages/contracts/src/config.ts` + defaults `DEFAULT_SYSTEM_CONFIG` in `packages/domain/src/config.ts`), grouped by domain:
- `evaluation`: `defaultMacroF1` (`0.80`), `customStartValueF1` (`0.60`), `customStartPrecision` (`0.70`), `customStartRecall` (`0.70`), `invalidRateCap` (`0.01`).
- `dataset`: `minEvalHard` (`4`), `minEvalRecommended` (`20`), `rareValueMinCount` (`4`), `rareValuePerHalfMin` (`2`), `dominantValueShareWarn` (`0.70`), `dominantWarnMinLabeled` (`30`).
- `optimiser`: `defaultMaxRounds` (`10`), `maxRoundsCap` (`50`), `stepRetries` (`3`), `wastedRoundsLimit` (`3`), `consecutiveTiesLimit` (`2`), `mergeEveryKept` (`2`), `dryRunMaxExamples` (`20`), `lowestFieldWeight` (`2`), `briefWrongExamples` (`8`), `briefMergeWins` (`4`), `briefMaxImages` (`2`), `briefFeatureMaxChars` (`300`).
- `labeling`: `defaultParallel` (`4`), `maxFailedShare` (`0.05`), `maxFailedInARow` (`20`), `stopCheckMs` (`2000`), `reasonMaxChars` (`300`), `commentMaxChars` (`500`).
- `gateway`: `assumedLimits` (per-model QPM/TPM/concurrency), `windowMs` (`60_000`), `retryDelaysMs` (`[2000, 4000, 8000, 16000]`), `imageTokensEstimate` (`800`), `charsPerTokenEstimate` (`4`), `evalOutputTokensEstimate` (`150`).
- `agent`: `maxToolCalls` (`4`), `maxToolResultChars` (`12_000`), `recentHistoryCount` (`8`), `maxDocChars` (`20_000`), `maxAttachmentChars` (`8_000`), `tryTemplateMaxExamples` (`5`).
- `ui`: `activePollMs` (`5000`), `sweepMs` (`60_000`), `changeDebounceMs` (`120`), `minActionPendingMs` (`220`).

Expose optional `config?: DeepPartial<SystemConfig>` on `Platform` (`packages/contracts/src/platform-api.ts`) merged over `DEFAULT_SYSTEM_CONFIG` at startup so hosting adapters can tune parameters dynamically without code edits.

**Phase 1 status (2026-11-12): built.** `SystemConfig`, the ID-only plain-JSON `BffContract` with request structs and idempotency keys, `createBffApi`, the `BffClient` split, `apps/optimiser` behind `OptimiserContract`, the enterprise ports, and the removal of the budget shim, `reopenGold`, `Recommendation` and dead telemetry entries. Notes for the later phases:
- `apps/optimiser` gets one more injected port than 7.2 lists, `OptimiserHost`: the bff keeps the rules for saving a version, labeling and scoring, and the Optimiser asks for them, instead of copying them.
- Moved to phase 2, because they change screens or types that phase rewrites anyway: removing the Setup and Training Set routes and their services, `checkLabels`, `FeatureValue` in place of the `string | string[]` feature union, the typed `StructuredPromptProposal` payload, and the callback-free `runTurn`.
- The services' sync live getters (`agentLive`, `isAgentBusy`, `answeringAgent`) stay on the web `BffClient` as a cache of the event stream; the contract has `getAgentLive` and `getAnsweringAgent` for an HTTP client to fill it.

**Existing `0.x` projects:** the spec defines no migration. Assumption until the owner says otherwise: `0.x` projects are test data and are discarded when phase 2 ships.
