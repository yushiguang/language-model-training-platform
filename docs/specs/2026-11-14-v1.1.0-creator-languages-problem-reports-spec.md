# Specification: Sprint `v1.1.0`: Project Creator and Rename, English and Chinese, Problem Reports

**Target Release:** `1.1.0` (minor: additive features on top of `1.0.0`)
**Date:** 2026-11-14
**Target:** External Agent (contracts, domain, services, agents and web app)
**Contract Impact:** Additive (`Contract change (v1.1.0): renameProject, locale, client diagnostics, TicketPort, report_problem`). One field is added to `SendMessageRequest`, `ChatMessage` and `AgentTurnInput`; nothing is removed or renamed.

Decided with the owner on 2026-11-14:
- The Projects list shows who created each project. No more than that until tenants arrive.
- A project is renamed in Project Settings, not on the top island.
- The site speaks English and Chinese. More languages come later as new catalogs.
- Reporting a problem is a tool every helper can use, not a separate helper. The site defines the
  ticket submission interface; the internal platform files the ticket. The user gets a ticket id.
  There is no reports page.

---

## 1. Project Creator and Rename

### 1.1 Creator
- `Project.createdBy` already holds the creator's display name. `Project.createdById` (new,
  optional) holds the user id, so a later tenant model can check ownership without matching names.
- The Projects list gets a **Created by** column between Project and Created.

### 1.2 Rename
- Project Settings gets a **Name** field at the top of the dialog, prefilled with the current name.
- Saving the dialog with a changed name calls `renameProject({projectId, name})`. The name is
  trimmed, must not be empty, and is cut at `project.nameMaxChars` (default 80). Names need not be
  unique; the project id never changes.
- The rename is written to the audit log (`project.rename`) and as the event `project_renamed`
  (no name in telemetry).
- Tenants (later): `RequestContext` already carries the tenant. Projects will gain `tenantId`, the
  list will show the tenant's projects, and only the creator or a tenant admin may rename or delete.

## 2. English and Chinese

### 2.1 Catalogs
- English is the source language: every UI string is its own key. `packages/domain/src/locales/zh.ts`
  maps each English key to Chinese. A key with `{name}` placeholders is filled from params.
- `translate(locale, key, params)` in `@tsp/domain` returns the Chinese text when the catalog has
  it, else the English key filled in. A string param that is itself a catalog key is translated
  too (so "{who} put a draft on {page}" reads right with the helper and page names in Chinese).
- The catalogs are the one exception to the repository's "English only" rule (AGENTS.md).
- The Chinese terms for the step names, helpers and core words are fixed once in the catalog (its
  first block) and the helpers' language line is built from the same entries, so pages and
  helpers use the same words.

### 2.2 The switch
- The user's avatar on the top island opens a small menu: the user's name, then **Language** with
  "English" and Chinese, each written in its own language.
- The choice is kept in the browser (`tsp-locale`). With nothing kept, a browser whose language
  starts with `zh` starts in Chinese. Switching re-renders the page in place; `<html lang>` follows.
- The static export is built in English, so a Chinese user sees English for the first paint only.

### 2.3 What is translated
- Every page, dialog, hover, empty state, badge and banner.
- Texts the services make: action lines in Ask AI and the AI Suggestion card carry a `Msg`
  (`{key, params}`) next to their English text, and the web shows the translation. Known error
  messages are catalog keys too.
- Helper replies follow the user's language: `SendMessageRequest.locale` reaches the agent runtime
  (`AgentTurnInput.locale`), and the helpers are told to answer in Chinese with the site's Chinese
  page names. Prompts, label fields, values and examples stay in the language the user wrote them.
- Not translated in `1.1.0`: the Optimiser's change notes and Improve with AI's change reasons
  (they describe prompt text, which keeps its own language), model names, and data.

## 3. Problem Reports

### 3.1 The flow
1. On any page, the user tells Ask AI that something is wrong, or asks to report a problem.
2. Whichever helper answers asks, if needed, what the user expected and what happened, then calls
   `report_problem` without `send`. The site returns a draft, and the helper shows its summary in
   the reply and asks whether to send it (and, when it matters, whether to include the prompt).
3. Only after the user says yes does the helper call `report_problem` with `send: true`. Code
   refuses a send unless a draft exists and the user has written since it was made, so a helper can
   never send in the same turn it drafted.
4. The reply gives the ticket id. An action line records it: "You sent a problem report T-…".

### 3.2 What a ticket holds (`TicketSubmission`)
- **The user's account**: summary, expected, actual, steps (rebuilt from the action trail and the
  conversation), the reporter (id and name) and the locale.
- **Where**: app version, project id, the page and its ids (version, model), the steps approved,
  the settings in short.
- **What happened just before** (`ClientDiagnostics`, collected in the browser): the path, browser,
  viewport, screen and time zone; the last 10 pages visited; the last 10 failed backend calls with
  their method, call id and error; the last 10 script errors. The recent Ask AI action lines are
  added by the bff.
- **Content only when the user agrees** (`includeContent`): the compiled prompt of the version in
  question. Never examples' features or gold labels in `1.1.0`.

### 3.3 Interfaces (`@tsp/contracts`)
- `TicketPort.submit(ticket: TicketSubmission): Promise<{ticketId: string}>` on `Platform.tickets`
  (optional). The stand-in keeps tickets in the browser (`tsp-tickets`) and makes ids like
  `T-4F7K2Q`. Without a port the tool tells the user reports cannot be sent here.
- `SendMessageRequest.client?: ClientDiagnostics`: the web client attaches its rolling record to
  every Ask AI message. The bff keeps it for the turn only and never stores it.
- Every bff call gets a call id in the client. An HTTP client must send it as `X-Request-Id`, so
  server logs and the ticket's failed calls point at the same request.

## 4. Telemetry
New events, counts and enums only: `project_renamed`, `locale_changed` (`locale`),
`problem_report_drafted` (`page`), `problem_reported` (`page`, `has_content`, `failed_calls`,
`errors`). New tool label value: `report_problem`.

## 5. Contract Changes (all additive)
- `types.ts`: `Locale`, `Msg`, `ClientDiagnostics`; `Project.createdById?`; `ChatMessage.msg?`.
- `bff-api.ts`: `renameProject(req: RenameProjectRequest)`; `SendMessageRequest.locale?`,
  `SendMessageRequest.client?`.
- `agent-api.ts`: `AgentToolName` gains `report_problem`; `AgentTurnInput.locale?`.
- `platform-api.ts`: `TicketPort`, `TicketSubmission`, `Platform.tickets?`.
- `telemetry.ts`: the events and tool value above.

## 6. Verification
- Unit: `translate` fills params and translates params; every key the services build is in the
  Chinese catalog; rename trims, refuses empty and audits; `report_problem` refuses a send in the
  drafting turn and sends after a user message; tickets carry diagnostics and no content unless
  asked.
- Browser check: the Created by column; rename from Project Settings shows on the top island; a
  problem reported from Ask AI returns a ticket id and the stored ticket holds the page, failed
  calls and no prompt; switching to Chinese shows the Chinese step names and no catalog misses on the
  pages visited, then back to English.

## 7. Status
Built on 2026-11-14 on the 1.0.0 branch (PR #6), after the owner's go. Versions stay below 1.0.0
until the combined acceptance; then `1.1.0` follows.
